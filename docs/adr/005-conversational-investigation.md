# ADR 005: 会話型の分析と番号付き根拠

## 判断

分析1ターンで単純SELECTまたは最大4本の独立SELECTを計画し、すべてを事前検証してから順番に実行する。実行後に番号付き根拠をモデルへ渡し、回答・発見・制約・次の質問を構造化して生成する。回答は既存の単一表・SQLフィールドを維持しつつ `evidence` と `report` を追加する。

確認・拒否を含む直近6ターンを保持し、説明だけの依頼は `explain` として既存の標本に基づいて回答する。条件変更時は新しいSQLを生成する。履歴は権限の根拠にならない。エラーは文脈から除外する。

## 安全性と上限

- 計画内の全SQLをAST事前検証。1本でも危険なら0本実行。
- 各実行・各修正もAST検証と読み取り専用DBロールを通す。
- 計画は最大4本、修正はターン全体で最大3回（1本ごとに3回ではない）。最大7回のDB実行。
- 修正に渡すDB情報はSQLSTATEと対象SQLのみ。権限・タイムアウト等は修正しない。
- 途中の失敗では完了した根拠を残すが、全体の結論を生成しない。
- 根拠番号の範囲外参照は解説失敗扱い。番号の妥当性は検査するが文章と数値の整合性の完全検証ではない。
- 解説に使う結果は各25行まで。履歴の根拠は各8行・8列・セル200文字・SQL4,000文字まで。省略を明示。
- 履歴JSONは48,000文字まで、HTTP本文は64,000の上限を設ける（Content-Lengthはbytes、読み込み後は文字数）。
- 全体の120秒上限、各SQL5秒、同時実行2件を維持。

## 取引条件

計画→複数SQL→統合は実装するが、途中結果を見て無制限に次の調査を選ぶ自律ループではない。追加調査は利用者の追質問・提案ボタンから始める。実行回数・利用枠・待ち時間を予測しやすくするための選択である。

自由な分析質問は受け付けるが、スキーマは架空ECの5表に限定する。CSVの任意取込み、汎用チャット、永続履歴、実データでの業務効果や因果推論は別途設計・検証が必要。ブラウザの会話はリロードで消える。

## 評価

既存50問は開発済みの回帰セット。追加の会話セットは初回実行時のみ未使用の質問として扱い、プロンプトとsuiteのSHA-256を保存する。正解SQLは判定側のみが使う。失敗後の再実行を新しい未見精度と称さない。

数値・拒否・確認・実行数・根拠の存在は自動評価。因果制約のキーワード検査は最低限の補助であり、説明の意味的正確性は人が確認する。AI支援で作られた成果物と作者自身の理解・再現能力は区別する。
