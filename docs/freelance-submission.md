# 日本語データ分析エージェント — 提出用説明

## 何を解決するか

対象は、ECの売上確認を担当し、SQLを直接書く機会が少ない運用担当者。毎月の「売上はどう変わったか」「どの地域・カテゴリが数値変化に寄与したか」という確認を、日本語で依頼し、SQLと結果を検証できる形で受け取るための技術デモです。

**実顧客への導入実績、削減時間、契約獲得実績はありません。** 架空データで、質問→計画→安全な集計→根拠付き回答→深掘り→メモ保存の業務フローを示します。導入効果は実際の担当者との試験で測定する必要があります。

## 2〜3分のライブデモ

1. 実AIモードを開く。固定回答デモではないこと、架空データ・基準日2026-10-01を説明する。
2. 「先月の売上が落ちた理由を調べて。前月と比較し、月別売上・地域別の差額・カテゴリ別の差額を独立した3つの集計で示して。」と依頼する。
3. 実行された複数の根拠を開き、結果とSQLを示す。増減の数値分解と、広告等の原因を断定できない点を区別する。
4. 「同じ期間、東京だけのカテゴリ別の差額を調べて」と続け、文脈を引き継いだSQLを確認する。
5. 「この結果だけで広告が原因と断定できる？追加集計せず説明して」と質問し、根拠と追加データの必要性を確認する。
6. 「分析メモを保存」で、質問・結果・根拠SQL・制約・実行情報を持ち帰れることを示す。

時間がある場合は新しい分析で「人気の商品を知りたい」→確認→「2026年2月の販売数量で上位5つ」と返し、確認の文脈が消えないことを見せる。削除要求は実行されないことも示す。

AIが質問を誤解した場合は隠さず、SQL・条件を確認して修正依頼する。録画・スクリーンショット・固定デモを実AIの成功実績と混同しない。

## 実装として示せること

- UIとは独立したハーネスと、Claude / ChatGPTの差し替え可能なアダプター。
- 単純集計と最大4本の調査計画、全体3回までのSQLSTATEベース修正、途中失敗の扱い。
- AST検証とDB読み取り専用権限の二重防御。認証、Origin、同時実行、SQL時間・出力の上限。
- 確認を含む会話履歴、根拠番号付き回答、制約と次の調査、根拠ごとのCSVと分析メモ。
- 結果比較によるAI評価、実PostgreSQLテスト、ブラウザE2E、検証証跡。

最新の実測は [検証記録](verification.md)。既存50問の過去の100%を、拡張後のコードや任意の業務への100%と説明しない。会話評価は別のセットと実行記録で示す。

リポジトリ内に [初回会話評価の実応答](evidence/conversations-first-pass.json) と [実画面デモに使った応答](evidence/presentation-demo.json) を同梱しています。どちらも架空データです。スクリーンショットを再現するにはローカル画面を起動して `npx tsx scripts/capture-conversation.ts` を実行します。この再生はAIを呼ばず、AI精度の追加測定ではありません。

## 導入前に決める条件

| 条件       | このデモ                                            | 実導入前に必要なこと                                             |
| ---------- | --------------------------------------------------- | ---------------------------------------------------------------- |
| データ     | 固定の架空EC5表                                     | 対象DB、売上定義、返品・税・通貨・日時の合意、対応スキーマの実装 |
| 権限       | 専用readonlyロール・ローカルトークン                | 個人認証、所属別アクセス、監査ログ、秘密の保管方針               |
| AI接続     | 本人のChatGPT/Codexログイン、または本人のClaudeキー | 顧客環境に適した接続と利用条件、組織のデータ送信承認・機密区分   |
| 実行環境   | このMacの画面/API/DB、推論はクラウド                | 配備先、障害対応、バックアップ、共有レート制限、運用担当         |
| 品質       | 固定データの自動評価                                | 顧客の未見質問で受入試験、誤回答時の人による確認フロー           |
| 履歴       | ブラウザ内の直近6ターン、リロードで消える           | 保存期間、削除、暗号化、共有の要否                               |
| 費用と効果 | サブスク消費、API換算なし、業務効果未測定           | 月間件数と予算の上限、手作業との比較測定                         |

このサブスク接続を不特定多数へ提供する構成はありません。実顧客データの投入や外部公開は、このローカル検証の許可とは別に判断します。

## レビュー時の再現方法

`npm run typecheck`、`RUN_POSTGRES_TESTS=1 npm test`、`npm run build`、`npm run test:e2e`。実AIの確認は利用枠を消費するため明示的に `npm run test:live`、`npm run eval:conversations` を実行します。セットアップはREADME参照。

会話評価ではモデルへ質問と履歴だけを渡し、正解SQLを渡しません。レポートは `reports/conversations-*.json` に条件・ソース/プロンプト/suiteのSHA-256・各ターンの合否・実応答を保存します。再実行は回帰評価です。

## 作者の実力として説明する際の注意

このプロジェクトはAI支援で実装・検証しています。成果物だけで作者自身の設計・実装力すべてを証明するとは主張しません。次の内容を自分の言葉で説明し、変更を再現できることが信頼につながります。

- モデルにDBの書込み権限を与えない理由と、ASTだけでは不十分な理由。
- SQL修正と、権限・時間切れのエラーを分ける理由。
- 「寄与」と「原因」の違い、数字が正しくても説明が誤る可能性。
- 新しい指標を1つ追加し、その正解SQLとテストを書けること。
- 上限・認証・履歴保存を実導入の条件に合わせて変更できること。

採用や契約の保証ではなく、設計判断と再現可能な検証を材料として提示します。
